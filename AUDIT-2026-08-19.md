## Findings closed

### 1. Anyone signed in could promote themselves — `user_metadata.role` (critical) · #74, #75

Four pages — sandouk, dashboard, water-admin, mrs — decided who may enter by reading
`user_metadata.role`. Supabase lets a signed-in user rewrite their own metadata from the browser
console, so one line in DevTools turned a resident account into a mayor and opened the cash box,
the dashboard, the irrigation admin and the financial archive. Three further pages — news-admin,
admin-push, inbox — asked only whether the visitor was signed in at all.

**Closed by** moving the decision to the server. `user_roles` is now the single source of truth,
with `role_permissions` (defaults per role) and `user_permissions` (per-person overrides) beside
it; `has_perm()` resolves *override → role default → false*. `wadi-perms.js` gives the pages the
same resolution, so a page and the database can no longer disagree about the same person.

| page | requires now | before |
|---|---|---|
| sandouk | `sandouk_view` | metadata role |
| dashboard | `cases_view` / `water_view` / `sandouk_view` | metadata role |
| water-admin | `water_view` | metadata role |
| mrs | `mrs_view` | metadata role |
| news-admin | `news_publish` | **any signed-in account** |
| admin-push | `push_send` | **any signed-in account** |
| inbox | `inbox_read` | **any signed-in account** |

### 2. The database only checked "is logged in" (critical) · #76

Most municipal tables were governed by `auth.uid() IS NOT NULL` — a test for *being* logged in, not
for *being allowed*. Any account, including a resident who registered on the public citizen page,
could:

- read and write the entire cash box,
- rewrite or delete any citizen case file,
- insert itself into `employees` as `manager` — which is exactly the check the `admin-user` edge
  function trusts before it will create or delete accounts.

The role-checked policies sitting beside these were decoration: policies combine with OR, so the
loose one always won.

**Closed by** `08_lock_down_policies.sql` — every table decides through `has_perm()` / `has_role()`.
Verified with simulated sessions: mayor sees 163 vouchers and cannot add, edit or delete;
treasurer and sandouk see, add and edit but cannot delete; a water-only account now sees **0**
(was: all 163); an account with no roles sees 0; anonymous sees 0. The three escalation attempts
(insert into `employees` as manager, insert into `super_admins`, insert into the cash box) are all
blocked — **all three previously succeeded.**

### 3. The cash box leaked through its own audit trail (critical) · #80

The money tables were locked. Everything beside them was not.

| table | policy was | what leaked |
|---|---|---|
| `baladieh_finance_audit` | `select using (true)` | **168 of 173 rows carry `amount`, 166 carry `person`** — the cash box in full |
| `mrs_*` (28 tables) | `select using (true)` | the taxpayer registry, **209 names** |
| `audit_log` | `select using (true)` | **1,727** rows of system activity |

Anyone able to create an account — a coop seller, for instance — held all three.

**Closed by** `09_close_audit_and_registry_leaks.sql`, giving each the permission its own page
already requires. Verified both ways: an ordinary account reads 0, 0, 0; a real sandouk staff
account still reads 163 finance rows, 173 audit rows and 209 registry rows. **Nobody legitimate
lost access.**

### 4. Residents' personal details were readable by anyone (critical) · #81

`cases` had `select using (true)` for `anon` — all 39 records with **name, phone, email, address
and description**, readable by anyone holding the public key, and the ids are sequential so they
could simply be walked. The push deeplink was worse: `?case=ID` rendered the whole request with no
check at all. The tracking screen already asked for a phone number, but checked it in JavaScript
*after* fetching the row.

**Closed by** moving the check into the database — `citizen_track_case(p_ref, p_phone)`, security
definer, returns nothing on a phone mismatch. The citizen's experience is unchanged. Anon keeps a
10-minute, **id-only** window, which is what `INSERT … RETURNING` needs to hand back a case number
and nothing more. Alongside it: `irr_owners` keeps its rows public but loses `phone` / `email`;
`push_subscriptions` keeps the device token and loses `user_name` / `user_phone`; and
`coop_orders_delivery_claim` — which checked only that an order *was* a delivery, **with no auth
test at all**, so anyone could reassign or complete any delivery — now requires `auth.uid()` like
every other coop write.

**Verified:** anon reads **0** cases and cannot read `name`; staff still read all **39**; the
lookup returns the request for the right phone and **0** for a wrong one.

### 5. The coop seller login handed out password hashes (critical) · #82

```js
const res = await sb.from('coop_sellers').select('*').eq('username',u).single();
if (res.error || !res.data || res.data.password_hash !== hash) { …reject… }
```

`coop_sellers` is readable by `anon`, so **every seller's `password_hash` was downloadable** by
anyone with the public key — unsalted SHA-256, a rainbow-table lookup away from the password
itself. And because the comparison happened in the browser, an attacker did not even need the
password: writing `localStorage.coop_seller` was enough. Confirmed before fixing:
`has_column_privilege('anon','coop_sellers','password_hash','select')` → **true**, on all 3 sellers.

**Closed by** `coop_seller_login(p_username, p_password)` — security definer, hashes and compares in
the database, the same shape delivery agents already used. `password_hash` and `pin_hash` are no
longer granted to `anon`; display name, area and whatsapp still read as before.

### 6. The municipality's own domain could redirect anywhere · #80

Anonymous visitors could insert into `short_links`, and the redirect edge function 302s to whatever
`url` the row holds with no allowlist — so a municipal link could bounce people to any site. All 8
existing rows already point at project storage, so constraining it to this project's own storage
cost nothing.

### 7. A second tap banked the same receipt twice · #80

`bfSave` and six sibling handlers were wired straight to a button and `await` a network insert with
nothing guarding re-entry. A second tap before the first returns — routine on a phone with a weak
signal — created a second record. Guarded: `bfSave`, `bfEditSave`, `saveExpense`, `saveCollection`,
`doSubmitCit`, `submitCitUpdate`, `submitAdd`. **No duplicate exists in the live data** — no
repeated `receipt_no`, no identical entry pair within 20 seconds. Driven in Chromium: three rapid
taps on حفظ now create one record.

### 8. 1.2 MB of stale archives served from the web root · #80

Four zips were publicly downloadable, holding frozen copies of index, dashboard, citizen,
water-admin, mrs and sw.js from before the permission work. Checked before removing: every JWT
inside is the anon key already public in the page source. **No elevated credential leaked** — dead
weight and old code, not a breach. Removed, and `*.zip` added to `.gitignore`.

### 9. User management could never have worked · #73

`إدارة المستخدمين والأدوار` failed with `خطأ: Invalid or expired session` for every account,
including the owner's: `adminAPI()` sent the public **anon key** as the bearer token. The older
employee screen was worse — `loadEmp`, `chRole`, `saveEmp` and `delEmp` called the GoTrue admin
endpoints directly with the anon key, which requires the service role, so they could never have
worked at all. All now go through the live session's access token.

### 10. Roles that existed in one place and not the other · #77, #78

Creating an employee set the role in `user_metadata` only — nothing wrote `user_roles`, so a new
employee could sign in and open nothing, with no visible reason why. Account creation now writes
`user_roles` (and says so if that write fails), deletion clears `user_roles` and `user_permissions`
rather than orphaning them, and the employee list shows the role the **server** holds.

## Checked and found clean

- No `service_role` key anywhere in the client; the edge functions read it from env.
- Privilege escalation blocked: `user_roles`, `user_permissions` and `role_permissions` writes all
  require `has_role(['mayor','admin'])`.
- Anonymous visitors cannot *write* to the coop — probing as `anon` modifies **0** rows on
  products, orders and sellers.
- Money arithmetic: USD and LBP in separate accumulators, never mixed; voided entries skipped; the
  running balance runs over the full ledger before filtering, which is the correct accounting choice.
- Cash-box data integrity: 163 entries, no null or negative amounts, no bad currency or type, no
  stamp exceeding its total.
- Coop and phonebook: no orphan sellers, no negative stock, no zero prices.
- All 25 pages parse; no JS errors on any page after these changes.
- The audit trigger still records through the new policies (a voucher inserted and updated as the
  treasurer produced 2 audit rows).

## Two corrections to earlier claims, recorded

- **The five "duplicate" residents are five real pairs of people**, not records entered twice. The
  comparison that made them look identical tested fields these records do not have. E.g.
  `ايلي يعقوب جوهر` — born 30/8/1989 to نورما خليل, and born 11/10/1987 to نجات مسلم. Different
  mothers, different birth dates, different registry ids, sharing a household phone. The payer
  picker now keys on each record's own id, so all **601** are selectable (up from 596) and shows
  the birth date where a name is shared. **There are no directory duplicates to remove.**
- **Anonymous visitors cannot write to the coop.** An earlier probe suggested otherwise; it counted
  an UPDATE that RLS had filtered to zero rows as a success. The one genuine anon write path was
  `coop_orders_delivery_claim`, closed in #81.

## Still open — these need your decision

### A. Coop sellers and delivery agents are not really logged in

They are identified from `localStorage`; only the admin path uses Supabase auth. Two consequences:

1. `coop_orders` still exposes **buyer name, phone and address to anon**, because the seller and
   agent order lists read it that way. Locking it without real identity would break the shop for
   the whole village.
2. Because the coop's write policies only test `auth.uid() IS NOT NULL`, **any authenticated
   account can modify any product, order or seller.**

Fixing it means giving sellers real accounts — a change to how every seller signs in. It also needs
the **email-confirmation setting**, which lives in the Auth service and is not visible from the
database: if confirmation is required, synthetic seller addresses cannot be confirmed and new
registrations would silently fail to log in. Not something to guess at on a live shop.

### B. Tables belonging to the other application in this Supabase project

Inventory, production, invoices, machines, suppliers, quality controls and time sessions still
carry `auth.uid() IS NOT NULL`. They are not part of this repository, and tightening what cannot be
tested here would be reckless. They are listed for that project's owner.
